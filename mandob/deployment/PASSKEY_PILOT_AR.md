# بديل Access: مفاتيح مرور للمسؤول — 21 نوفمبر 2026

هذا المستند يستبدل اقتراح Access/Zero Trust في إعداد تجربة Mandob. لا تسجيل Zero Trust ولا بطاقة ولا مزوّد دخول خارجي. لا نشر أو إنشاء موارد سحابية في هذه المرحلة، ولا تغيير لمشروعات وسيط وSocial Plus.

## ما نُفذ
- ADMIN_AUTH_MODE=passkey هو الإعداد المقترح في مولّد إعداد Free. يتحقق الخادم من أصل HTTPS ثابت وRP ID مطابق، ولا يستنتج الأصل من هيدر Host الذي يرسله العميل. إعداد الأصل النهائي مطلوب قبل التفعيل.
- تحقق WebAuthn بمكتبة @simplewebauthn/server 13.3.3 المثبتة في lockfile؛ لا كتابة تحقق تشفير خاص للإنتاج. ES256/مفتاح منصة مقيم وUser Verification مطلوبة. التصديق none لتقليل التتبع، وليس ادعاء مصادقة جهاز Apple أصلي. يمكن أن يختار النظام Face ID أو رمز الجهاز؛ Face ID ليس مضموناً أو مفروضاً حصراً. البيانات الحيوية والمفتاح الخاص لا تصل إلى Worker/D1.
- أول تسجيل يحتاج رمز عشوائي 256bit، صالح 10 دقائق ويستهلك مرة واحدة. لا يوجد endpoint لإنشاء الرمز أو فتح تسجيل مسؤول؛ يولّد المشغّل الرمز محلياً ويضع تجزئته في D1 المستقلة بعد الموافقة. الرمز ليس كلمة مرور مشتركة للدخول، ولا يوضع في URL أو Git أو السجلات. بيانات الاعتماد محدودة بمسؤول واحد ومفتاح مرور واحد حالياً؛ أي استرداد أو تبديل استثنائي يمر بالمشغّل المخوّل عبر Cloudflare، لا بباب استرداد عام.
- التحديات عشوائية 256bit، صالحة 5 دقائق، مربوطة بالمتصفح عبر Cookie عشوائية HttpOnly/Secure/SameSite=Strict ذات بادئة __Host-. تُحذف ذرّياً قبل التحقق، حتى عند الفشل. يتحقق origin وRP ID ونوع العملية وUV والتوقيع، ويمنع استغلال إطار خارجي. إعادة نفس الاستجابة أو طلبان متزامنان لا يحققان دخولين. عداد المصادق يُحدّث مع تحقق من القيمة القديمة؛ عداد 0 في المفاتيح المتزامنة يُعامل وفق المكتبة، وليس كدليل استنساخ قاطع.
- جلسات عشوائية 256bit، مدتها القصوى ساعة واحدة، token مجزّأ فقط في D1، وCookie __Host-mandob_session ذات HttpOnly/Secure/SameSite=Strict وPath=/. لا localStorage. CSRF عشوائي لكل جلسة، مع تحقق Origin وX-CSRF-Token لكل عملية معدِّلة. لا CORS مفتوح. الخروج وإلغاء جميع الجلسات يعملان على الخادم فوراً.
- اللوحة وملفاتها وAPI محمية؛ الصفحة العامة الوحيدة للدخول وسكربتها ومسارات المصادقة لا تعرض بيانات بائعين. معرفة الرابط أو هيدر بريد أو PSID أو ADMIN_TOKEN لا تمنح صلاحية في وضع passkey. السر القديم محصور بوضع اختبار محلي صريح LOCAL_TEST_ONLY=true؛ ليس مسار دخول إنتاج.
- حد المصادقة 10 محاولات POST لكل IP في نافذة 15 دقيقة و60 إجمالاً، مع تنظيف سجلات مؤقتة منتهية. تُشتق IP من هيدر Cloudflare على البيئة الحقيقية ولا تُسجل بصورتها الخام. هذه حماية تخمين/إساءة محدودة، وليست ضمان منع DDoS أو استنزاف حصة D1 المشتركة. بلوغ Free يعني توقف الخدمة، لا فوترة أو ترقية.
- Messenger مستقل: لا Cookie مسؤول ولا WebAuthn في مساره، بل تحقق Meta من التوقيع وصفحة الاستقبال. يظل ALLOW_MESSENGER_INTAKE=false في إعداد التجربة، وكذلك الإرسال الخارجي والصور وAI افتراضياً.

## D1 والترحيلات
0005_passkeys.sql إضافة فقط: رمز تهيئة مجزأ، مفتاح عام ومعرّف اعتماد للمسؤول، تحديات مؤقتة، جلسات مجزأة، وعدّاد محاولات. لا private key ولا صور Face ID. لا تغيير لسجلات البائعين والأغراض. طُبقت الترحيلات الخمس على D1 محلية فقط.

قبل أي SQL سحابي: التحقق من هوية mandob-baghdad-db الجديدة حصراً، وأخذ نسخة SQL إذا فيها بيانات. النسخة تشمل المفاتيح العامة؛ DATA_KEY منفصل وآمن. عند استعادة نسخة في الإنتاج تُلغى الجلسات والتحديات ورموز التهيئة المستعادة قبل فتح الخدمة، لمنع إعادة تفعيل جلسة قديمة أو رمز مستخدم. لا حذف لحسابات أو أغراض. خطة فقد المفتاح: تحقق هوية المسؤول عبر صلاحية Cloudflare الأصلية، إلغاء الجلسات ثم تبديل credential وإصدار تهيئة جديدة بعملية صريحة معتمدة؛ لا بريد استرداد عام أو كلمة سر بديلة. مزامنة iCloud Keychain قد تساعد على الاستعادة لكنها ليست خدمة يتحكم بها Mandob.

## نتائج الاختبارات
الاختبارات الأمنية تستخدم مفاتيح P-256 وCBOR وتواقيع WebAuthn اصطناعية قابلة للتحقق، وليست دالة verify تعيد true. تشمل التسجيل والدخول، origin الخاطئ، التحدي الخاطئ والمنتهي، التوقيع المزور، غياب UV، إعادة الاستخدام والتزامن، انتهاء الجلسة، تراجع العداد، CSRF، حجب بيانات الإدارة، وإلغاء كل الجلسات واستقلال Webhook.

اختبار كامل داخل bundle Worker الفعلي على workerd مع D1 محلية نجح في التسجيل والدخول وإلغاء الجلسات. حجم bundle نحو 731KB غير مضغوط، دون اعتماد خادم خارجي أو Node server في الإنتاج. قياس CPU داخل حد Workers Free الفعلي يبقى بوابة قبل فتح السحابة؛ لا يثبت الاختبار المحلي التكلفة أو الأداء على الحافة.

اختبار Chromium بمصادِق WebAuthn افتراضي وبعرض 390×844: تسجيل، دخول، ظهور اللوحة، إخفاء نموذج السر القديم، عدم كشف Session Cookie لـdocument.cookie، إلغاء الجلسات والرجوع للدخول، دون أخطاء JavaScript أو تمرير أفقي. النقل محلي باعتراض الاختبار، وليس اختبار TLS إنتاج. لم يُختبر Safari/iPhone/Face ID فعلياً.

npm audit أظهر صفراً من الثغرات المعروفة وقت الفحص؛ ليس ضماناً أمنياً شاملاً. لم يُجرَ اختبار اختراق أو استدعاء AI أو تواصل Messenger حقيقي.

## خطة التفعيل من الآيفون بعد الموافقة
1. نثبت مضيف HTTPS النهائي قبل التسجيل (المقترح Worker المستقل mandob-baghdad-api). تغيير المضيف لاحقاً قد يتطلب تسجيل مفتاح جديد؛ لا نعد بأن مفاتيح workers.dev تنتقل إلى دومين آخر.
2. بعد موافقة منفصلة: إنشاء Worker وD1 المجانيين فقط، الترحيلات والنسخة/الاسترجاع، وإعداد ADMIN_ORIGIN وWEBAUTHN_RP_ID والأسرار عبر قناة آمنة. لا Access أو R2 أو Queue أو بطاقة.
3. يجهّز المشغّل ملفات التهيئة الخاصة باستخدام prepare-enrollment.mjs محلياً؛ الملفات 0600 والدليل 0700، والرمز لا يُطبع. يطبق SQL المشروط على قاعدة Mandob فقط. لا تُنشأ هذه الملفات ولا الرمز الحقيقي الآن. تسليم الرمز للمسؤول يتم بقناة خاصة موثوقة خارج هذه المحادثة، ولا يرسله المسؤول هنا. إذا تعذر التسليم الموثوق نوقف التسجيل، ولا نفتح وصولاً عاماً بديلاً.
4. يفتح المسؤول /login في Safari حديث على آيفون مع قفل الجهاز وPasskeys مفعّلة. يفتح قسم التسجيل الأول ويدخل الرمز مرة واحدة، ثم يوافق على إنشاء مفتاح المرور باستخدام Face ID أو ما يقدمه الجهاز، ثم يضغط الدخول بمفتاح المرور.
5. نختبر معه تسجيل الخروج والدخول وإلغاء الجلسات؛ يختبر المشغّل رفض الوصول من متصفح آخر دون المفتاح. إذا أُلغي التسجيل بعد استهلاك الرمز، يلزم إصدار رمز جديد من المشغّل؛ لا يعاد استعمال القديم.
6. لا نقبل تجربة iPhone مكتملة قبل تأكيد نجاحها على الجهاز. تبقى Messenger والصور والردود وAI معطلة حتى اعتماد اختبارات كل تكامل على حدة. لا حاجة لتشغيل أوامر أو كتابة كود من الآيفون.
