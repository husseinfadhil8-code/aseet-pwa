# تشخيص فشل AI binding — 20 نوفمبر 2026

قراءة سجلات وكود واتصالات HTTP عادية فقط؛ لا إعادة استدلال ولا بدء Wrangler أو OAuth أو جلسة معاينة، ولا إنشاء موارد أو دفع أو نشر.

## الحكم

المثبت هو انقطاع نقل/اتصال أثناء تنفيذ binding، وليس فشلاً مثبتاً للنموذج أو اشتراط Paid. لا توجد أدلة كافية لعزل آخر hop المسبب أو إعلان سبب جذري نهائي. أقوى قرينة جديدة هي فشل HTTP العادي بالمسار المباشر مقابل نجاحه عبر وسيط البيئة؛ استخدام المسار الخطأ في أحد hops احتمال عملي، لا نتيجة مثبتة على طلب AI نفسه.

## أدلة المحاولة السابقة

- التوقيت تقريباً 23:31–23:33 بتوقيت بغداد. Wrangler 4.166.0، Miniflare 5.20261119.0-beta، workerd 1.20261119.1.
- ai.binding=AI مضبوط في config، وWrangler عرضه AI/remote. Worker المحلي استجاب، بعد إصلاح تصدير ثابت غير مسموح في ملف الدخول. ذلك الخطأ الأول منفصل عن فشل الشبكة اللاحق.
- لا ملف OAuth افتراضي محفوظ في المواضع القياسية أو مجلد config المعزول. المحاولة استعملت اعتماد البيئة، لا OAuth تفاعلياً. عدم وجود ملف لا يثبت وحده فشل المصادقة أو صلاحيات binding؛ ظهور Ready لا يثبت بدوره نجاح استدلال أو جميع خطوات الاتصال البعيد.
- الخطأ: InferenceUpstreamError / Network connection lost، مع stack يشير إلى Miniflare core/entry.worker.js عند service.fetch(request). كود المصدر في السطر 5499 ينتظر خدمة مرتبطة؛ لا يحدد وحده هل الانقطاع بين workerd وNode أم الـproxy أم الخدمة البعيدة.
- الغلاف أعاد HTTP 502 محلياً بعد حوالي 5057 و5060ms. الغلاف نفسه ينشئ 502 لأي exception؛ ليس HTTP status مثبتاً من Workers AI.
- لا upstream HTTP status أو cf-ray أو request/trace ID تابع لاستدلال Cloudflare محفوظ في السجلات المتاحة. معرفات Inspector/Isolate محلية وليست request IDs للجهة البعيدة. لا نعيد استخدام request ID لاتصال تشخيصي آخر على أنه يخص AI.
- إغلاق WebSocket بـ1006 ظهر مع إعادة تحميل الخادم المحلي. لا يكفي لاتهام الاتصال السحابي أو Access.
- التحليلات قبل/بعد أعادت قائمة AI فارغة؛ لا دليل أن الاستدلال وصل إلى النموذج، ولا إثبات قطعي لاستهلاك صفر بسبب تأخر التحليلات المحتمل.

## الشبكة وTLS

HTTP_PROXY/HTTPS_PROXY وNODE_EXTRA_CA_CERTS موجودة، وNO_PROXY يتضمن loopback. لم نطبع قيم اعتماد أو headers سرية أو سجلات خام. لا تعطيل للتحقق من TLS.

فحص GET عادي إلى https://www.cloudflare.com/cdn-cgi/trace، بلا رموز أو استدلال:
- Node fetch مباشر: TypeError، cause ECONNREFUSED.
- نفس URL عبر Undici ProxyAgent الخاص بوسيط البيئة: HTTP 200 مع cf-ray.

هذا يثبت فرق المسارين في البيئة الحالية، لا أن remote binding تجاهل الوسيط فعلاً. لا تعالج المشكلة بحذف proxy أو NO_PROXY أو تجاوز TLS عشوائياً. يجب تتبع hop الخاص بالـbinding نفسه عند جلسة تشخيص لاحقة معتمدة.

## Access والصلاحيات

المشكلة الرسمية #13642 توثق حظر remote bindings بواسطة Cloudflare Access. الكود المثبت يحتوي كشف redirect إلى cloudflareaccess.com وكشف 403/صفحة Cloudflare Access ورسالة تحذير واضحة. لم نجد تلك العلامات في سجل المحاولة. بيانات Service Token الخاصة بـAccess غير مضبوطة، وهذا لا يعني وجود Access application أو ضرورة إنشائها. لا ننشئ Access ولا نعطل حماية.

رفض REST القديم 401/403 يشير إلى مشكلة تفويض ذلك المسار، لكنه ليس HTTP status صادراً من binding في المحاولة الأخيرة ولا يثبت أن Network connection lost خطأ صلاحيات. يلزم في الاختبار اللاحق تسجيل نتيجة المصادقة/control-plane وcf-ray الآمن إن وصل رد، مع مراجعة OAuth أو الاعتماد بحسب الحاجة دون طلب أسرار داخل المحادثة.

## حالة الخدمة والمشكلات المعروفة

صفحة حالة Cloudflare وملخص API وقت الفحص يظهران Workers AI operational، ولم نجد حادثة AI في موجز الحوادث الحديث تطابق وقت المحاولة. توجد حادثة Event Subscription خاصة بتغييرات Workers ليست دليلاً على عطل استدلال. الحالة الحالية لا تنفي مشكلة عابرة أو إقليمية في الساعة السابقة.

لم نجد بلاغاً موثقاً يثبت أن Wrangler 4.166.0 نفسه يسبب هذه الحالة بالضبط. يوجد تاريخ لمشكلة Access ومشكلة race مع loopback keepAliveTimeout الافتراضي 5s ينتج عنها Network connection lost؛ لكن النسخة المثبتة تضبط server.keepAliveTimeout=0 بالفعل. لذلك لا ننسبها إلى العطل القديم لمجرد تشابه المدة. وجود Miniflare beta يجعل مقارنة إصدار موثق آخر خطوة تشخيصية محتملة، لا إثباتاً لخلل نسخة.

## خطة الإصلاح بالترتيب

1. تثبيت تسجيل آمن لاسم الاستثناء وcause/status ومرحلة الفشل والوقت، مع حذف Authorization وCookie وpreview tokens وMF-Proxy-Shared-Secret وأي URL query؛ لا نشر لسجلات Wrangler الخام.
2. في جلسة معاينة لاحقة معتمدة، اختبار مسار proxy غير المستدعي للنموذج أولاً، وإثبات المصادقة وصحة TLS/الوسيط والرد البعيد. Ready المحلي وحده غير كافٍ. إذا ظهر redirect/403 خاص بـAccess فتعالج السياسة عبر جلسة مخوّلة، لا بإيقاف الحماية. إذا لم يصل رد، يعالج النقل قبل زيادة الصلاحيات أو تغيير النموذج.
3. إعادة تقييم جلسة OAuth مخوّلة عند الحاجة، لا افتراض أن token العام يكفي أو أن OAuth مطلوب بالضرورة. لا مفاتيح في المحادثة.
4. إذا استمر الفشل مع النقل السليم، تقارن نسخة Wrangler/Miniflare موثقة أخرى في بيئة محلية معزولة مع نفس الحالة، دون تغيير التثبيت العام أو الإنتاج.
5. بعد إصلاح المسار، قراءة الحصة ثم اختبار استدلال واحد صغير فقط. لا ثلاث محادثات ولا fallback أو تكرار تلقائي قبل نجاحه.

## أقل اختبار فعلي مقترح، لم يُنفذ

نموذج Gemma-4-26B نفسه؛ طلب واحد فقط عبر env.AI.run، prompt اصطناعي «گول هلا فقط»، output حتى 32 tokens، ومهلة 30s دون retry. هدفه إثبات الاتصال ووصول رد وusage، لا تقييم ذكاء اللهجة. بعده تغلق الجلسة وتفحص الموارد والتحليلات.

إذا كان input نحو 128 tokens وoutput حتى 32، فالتقدير نحو 2.04 Neurons وفق المعدلات المراجعة، وليس استهلاكاً فعلياً أو سقفاً مضموناً. يخصص هامش 100 Neurons وتُقرأ الحصة قبل الطلب؛ عند عطل شبكة/طلب دفع/صلاحية غير متوقعة يتوقف فوراً. لا يغيّر هذا اعتماد المستخدم المطلوب لأي جلسة جديدة.
