# قاعدة وسيط المحلية ونظام migrations

هذه الأدوات للتطوير والاختبار المحلي فقط. لا يوجد project link ولا بيانات اتصال أو مفاتيح أو كلمة مرور للإنتاج في هذا التغيير. لا تنفذ الأدوات db push أو أي ترحيل إلى Supabase المستضاف.

لآلية Waseet-Test المنفصلة والمقيدة بالتفويض، راجع [WASEET_TEST.md](WASEET_TEST.md). المشغّل المحلي أدناه لا يتغير ولا يتصل بأي مشروع مستضاف.

## التشغيل

مسار قاعدة البيانات الموثق والمختبر مخصص لبيئة Linux مع Python 3 وDocker وcurl؛ ينسخ الملف التنفيذي Linux إلى حاوية Linux. مثبت CLI المستقل يدعم macOS أيضاً، لكن تشغيل القاعدة بهذه الأدوات على macOS غير مدعوم حالياً. يبقى التطبيق واجهة ثابتة؛ لا يحتاج npm أو حزم بناء.

```bash
python3 scripts/install_supabase_cli.py
docker pull postgres:17
PYTHONDONTWRITEBYTECODE=1 python3 scripts/local_database.py start
PYTHONDONTWRITEBYTECODE=1 python3 scripts/local_database.py status
PYTHONDONTWRITEBYTECODE=1 python3 scripts/local_database.py migrate
```

المثبت ينزل Supabase CLI الرسمي **2.75.0** ويتحقق من SHA-256 المثبت لكل منصة قبل استخراج الملف التنفيذي فقط. الملفات المحلية تحت `.local-database/` مستثناة من Git. اختيرت نسخة CLI محددة قابلة لإعادة الاختبار؛ لا يوجد تنزيل `latest` غير محدد أو تعطيل للتحقق من TLS/الـchecksum.

تنشأ قاعدة PostgreSQL 17 جديدة داخل حاوية بلا شبكة أو منافذ منشورة أو ملفات مضيف مركبة. تُنسخ ملفات migrations والملف التنفيذي إلى الحاوية ثم يعمل CLI **داخلها** متصلاً بـ127.0.0.1 الخاص بالحاوية. CLI قد يكتب “Connecting to remote database” لأننا نمرر db-url، لكن العنوان ثابت داخل الحاوية المعزولة؛ لا توجد وجهة خارجية يمكن الاتصال بها. اتصال loopback الداخلي دون TLS أو كلمة مرور، ولا تُمرر متغيرات المضيف أو أي مفاتيح Supabase إلى الحاوية.

يتحقق المشغّل من ملكية الحاوية وعزل الشبكة وعدم نشر منافذ، ويقبل migration up/list فقط، دون URL أو أسماء مشاريع من المستخدم. هذه قاعدة SQL للتطوير، وليست Supabase Studio أو REST/Auth/Storage API كاملة. `PLATFORM_FIXTURE` يحاكي الجداول والأدوار والدوال الدنيا auth/storage كي تُختبر SQL فعلياً؛ لا ينسخ بيانات الإنتاج. وجود دور SQL باسم service_role في الاختبار ليس استخداماً لمفتاح service_role، ولا تُنشأ مفاتيح JWT أو حسابات دخول حقيقية.

يستمر مثيل التطوير حتى يُوقف صراحةً. إيقافه يمسح **بياناته التجريبية المحلية فقط** ولا يمس مثيلاً آخر:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/local_database.py stop
```

مجلد `supabase/migrations/` هو مصدر التنفيذ المنظم. ملفات SQL القديمة بجذر supabase و`supabase-schema.sql` مراجع تاريخية لفهم المخطط والاختبارات القديمة، وليست خطوات تركيب تُشغّل بعد migrations. لا تُعد تشغيل fix_sales_permissions.sql بعد ترحيل المبيعات، لأنه يعيد منح INSERT المباشر. اختبارات الاتساق تتحقق أن نسختي المبيعات وRLS تطابقان المصدر المراجع حالياً. بعد اعتماد السلسلة لا تعدّل تاريخ migration مطبق: أضف migration جديداً.

لقطة الميزات تصلح خطأ محدد SQL في get_chat_people: استُخدم `$` بدلاً من `$$`، وكان يمنع إنشاء قاعدة جديدة من الملفات. لا تغير اللقطة منطق الدردشة أو الإشعارات الآخر. الترحيل الأمني يسمح بقاعدة profiles فارغة عند الإنشاء الجديد، لكنه يرفض قاعدة تحتوي حسابات دون أي مدير approved. لا يُنشأ مدير تلقائي في migrations؛ تستخدم الاختبارات حسابات اصطناعية داخل حاوياتها فقط.

## حماية الصلاحيات

معلومات المستخدم المؤكدة: profiles/goods/sales/notifications موجودة، RLS فعال، وسياسة Enable update for admin واسعة لجميع authenticated وسياسة Allow insert goods for authenticated تستخدم true، مع UPDATE لأعمدة role/status/permissions، ولا توجد مبيعات مكررة. استخدمنا هذه المعلومات دون الاتصال بالإنتاج.

السياسات permissive تتجمع بـOR، لذلك لا يكفي إضافة سياسة جديدة للمدير. الإصلاح يزيل الاسمين المحددين ويضع حدوداً RESTRICTIVE لا تتجاوزها سياسات السماح القديمة. UPDATE الصادر من المندوب لا يستطيع تغيير role/status/permissions/id، حتى من خلال دالة SECURITY DEFINER قديمة، بسبب مشغّل حماية يعتمد على هوية المستدعي الفعلية. إضافة الأغراض وتعديلها وحذفها للمدير approved، ويطابق created_by هوية المدير عند الإضافة.

يبقى منح UPDATE لدور authenticated المشترك ضرورياً لمسار إدارة المدير الحالي في الواجهة؛ الفصل الفعلي يحصل بواسطة RLS ومشغّل الأعمدة، وليس بادعاء أن المدير والمندوب دوران مختلفان في PostgreSQL. لو أُريد لاحقاً سحب منح الأعمدة من authenticated بالكامل، فيلزم نقل إدارة الحسابات إلى RPC مخصصة وتعديل الواجهة، وليس سحب المنح وحده وتعطيل المدير.

تسجيل العميل لا يقبل إلا rep/pending وصلاحية البداية المحددة لمعرفه نفسه. إدراج Auth الحقيقي من جلسة supabase_auth_admin دون JWT يُحوّل بيانات الدور والحالة والصلاحيات إلى القيم الآمنة، ويحافظ على بقية بيانات التسجيل. لا يستطيع JWT مزور في إعداد الجلسة انتحال دور خادم PostgreSQL الموثوق. تفاصيل الاختبارات الإضافية في RLS_PRIVILEGES_REVIEW.md.

## PR #6 والتوافق مع الإنتاج

فُحص الكود ووصف PR #6 المفتوح على main عند الرأس `046ef14`: https://github.com/husseinfadhil8-code/aseet-pwa/pull/6 . لا يتغير بروتوكول record_sale أو آلية العمولة عن الإصلاح المراجع؛ حصة الإدارة مشتقة والتحقق من المدير والمندوب والمبالغ داخل المعاملة. لا يُعاد منح INSERT للمبيعات. تشمل الاختبارات التنافس الحقيقي بين اتصالين والتراجع عن البيع والإشعارات عند الفشل. معلومة عدم وجود مبيعات مكررة متوافقة مع الحل؛ سجل الأهلية لا يتطلب حذف صفوف قديمة أو تعديلها.

**لم نثبت التطابق الكامل مع المخطط الحقيقي.** وجود الجداول وRLS والسياسات لا يحدد أنواع UUID/bigint/jsonb/timestamptz والقيم الافتراضية والمشغّلات ومالكي الدوال. المخطط الأولي يفتقد status/permissions رغم اعتماد التطبيق عليهما. القاعدة المحلية تعلن هذه الفرضيات صراحةً، ويوقف الترحيل الأمني التنفيذ عند عدم توافق متطلباته.

النسختان 00100 و00200 **لإنشاء قاعدة فارغة فقط**، ولا تصلحان للتطبيق فوق الإنتاج الموجود. يرفض اختبار إعادة bootstrap فوق جداول موجودة العملية دون تغيير البيانات. لا تستخدم migration repair لتمييز هذه اللقطة مطبقة لمجرد تجاوز الأخطاء. تبني تاريخ إنتاج موجود يحتاج مقارنة metadata/مخطط منزوع الأسرار ومراجعة منفصلة، ثم خطة baseline/upgrade معتمدة؛ لم ننفّذ adoption أو repair أو dump أو link أو push إلى الإنتاج.

قبل أي تطبيق مستقبلي، يلزم التحقق من أنواع الأعمدة وقيودها، وتعريفات triggers على auth.users/profiles/goods/sales، وسياسات ومنح الأعمدة والأدوار الموروثة، ومدير approved ومالك BYPASSRLS للدوال الجديدة. يمكن توفير هذه المعلومات كتصدير وصف بنيوي منزوع الأسرار في مهمة لاحقة، دون مفتاح service_role أو كلمة مرور مدير. نتوقف عند هذه الحدود ولا نحاول الاتصال الحقيقي لتخمينها. اختبارات GoTrue/JWT/PostgREST وتسليم Push الحقيقي لم تُنفّذ.

هذه حماية للمسارات المذكورة، وليست شهادة بأمان بقية الميزات القديمة. تبقى مراجعة سياسات رفع صور الجمهور المجهولة وخصوصية أعمدة اتصال أصحاب الأغراض وإبطال عضوية الدردشة للحساب المحظور أعمالاً منفصلة.

## الاختبارات وCI

```bash
PYTHONDONTWRITEBYTECODE=1 python3 scripts/integration_migrations.py -v
PYTHONDONTWRITEBYTECODE=1 python3 scripts/integration_rls_privileges.py -v
PYTHONDONTWRITEBYTECODE=1 python3 scripts/browser_app_security.py -v
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts -p 'test_*.py' -v
node --check app.js
git diff --check
```

اختبارات migrations تطبق الملفات الفعلية بواسطة CLI على قاعدة فارغة، وتفحص سجل النسخ وإعادة التطبيق وعدم تغيير البيانات والتزامن وحماية RLS والإشعارات والاستفسارات وصلاحية وظائف الدردشة. المجموعة الأمنية تعيد اختبارات PR #6 فوق RLS الجديدة وتختبر التسجيل والإدارة ومحاولات التصعيد والسياسات القديمة الواسعة. المتصفح يتطلب Playwright وChromium، ويستخدم backend وهمياً ويحجب الاتصالات الخارجية. كل قاعدة اختبارات مؤقتة تزال تلقائياً عند النهاية.

Workflow `database-tests.yml` يعمل عند Pull Request أو التشغيل اليدوي، دون أسرار أو بيانات اتصال إلى الإنتاج، ويثبت CLI ويتحقق من checksum ويختبر السلسلة وRLS. لا ينشر أو يدمج أو يغيّر Supabase المستضاف.
