## الإجراء المطلوب مرة واحدة

اختار المستخدم تجهيز **اتصال PostgreSQL ووجهة آمنة** في إعدادات البيئة. لم يُجهزا أو يُتحقق منهما بعد. لا ترسل القيم في المحادثة أو GitHub.

1. استخدام بيانات الاتصال الحالية لـ Waseet-Test من لوحة Supabase؛ يفضل session pooler عند غياب IPv6. ربط بيانات libpq كملفات سرية (service/pgpass) أو متغيرات خاصة، وليس وسيطات مطبوعة. الدور يجب أن يقرأ المخطط والبيانات اللازمة في public وauth وstorage وتاريخ migrations دون إخفاء صفوف بواسطة RLS، ومع رؤية الكائنات والملكية وACL. دور التطبيق أو Management token ليس بديلاً عن اتصال PostgreSQL. لا تطلب كلمة مرور جديدة لمجرد غياب الربط.
2. السماح بمضيف/منفذ اتصال المشروع المحدد عبر إعداد الشبكة المدعوم؛ سياسة TCP الحالية لا تتضمن وجهات. لا يكفي HTTP unrestricted لنجاح PostgreSQL. يلزم TLS والتحقق من شهادة الخادم؛ لا استخدام sslmode=disable أو تجاوز proxy.
3. تحديد وجهة مستقلة دائمة مشفرة يملكها المستخدم (خارج المستودع وCI العام)، وآلية التشفير/الاسترجاع أو مفتاح تشفير عام مناسب. ملف داخل /tmp أو قرص جلسة Codex وحده لا يحقق هذه البوابة.

لا نطلب مفتاح Storage حالياً لأن الجرد لم يجد ملفات مسجلة. إن ظهر أي ملف عند التصدير، يلزم مسار قراءة Storage مأذون من الحساب الحالي، وتنزيل كل الملفات المطلوبة مع SHA-256 وحجم ونوع ومفتاح الكائن إلى نفس الأرشيف المشفر؛ لا نجعل bucket عاماً ولا نستخرج service_role عبر Management لتجاوز حدود السر.

## مسار التنفيذ بعد تجهيز الربط

1. إعادة تحقق الهوية عبر Management، ومطابقة خدمة PostgreSQL مع معلومات اتصال المشروع التجريبي من اللوحة. فحص TLS والإصدار وRLS والحقوق. لا تخمين DSN ولا fallback إلى إعدادات CLI مرتبطة بالإنتاج.
2. استخدام pg_dump 17 لصنع custom archive متسق للمخطط والبيانات وAuth وStorage metadata وتاريخ التطبيق. رفض أي خطأ صلاحية أو كائن غير مقروء؛ لا تخطي جدول أو تعطيل RLS لإخفاء نقص التغطية. حفظ جرد الأدوار والمنح دون كلمات مرور الأدوار. عند فصل schema/data يلزم snapshot مشترك، لا dumps مستقلة توصف بأنها لقطة واحدة.
3. تضمين manifest بإصدار الأدوات، المرجع، وقت البداية والنهاية، نطاق المحتويات والاستثناءات والعدادات وبصمات الملفات. ضغط/تشفير النسخة وحفظها في الوجهة المستقلة، ثم تنزيلها منها والتحقق من البصمة وفكها بنجاح. لا طباعة سجل يحتوي صفوفاً أو hashes كلمات مرور Auth.
4. استعادة إلى قاعدة جديدة معزولة تماماً؛ `pg_restore --exit-on-error --single-transaction`، دون --clean على مصدر موجود أو تجاهل FK. يجب تجهيز أدوار وإضافات Supabase المتوافقة قبل الاستعادة؛ صورة PostgreSQL عادية لا تتضمن supabase_vault أو جميع خدمات المنصة. عدم استخدام --no-acl لإعلان نجاح اختبار الصلاحيات.
5. مقارنة المخطط والمالكين وACL/RLS والسياسات والدوال والمشغلات والقيود والفهارس والتسلسلات، وعدد الصفوف وبصمات محتواها والتاريخ. التحقق من روابط Auth وملفات Storage، واستكمال اختبار تسجيل الدخول والرفع/التنزيل على Supabase محلي/اختبار معزول عند الحاجة. استعادة auth.users في PostgreSQL لا تثبت عمل GoTrue أو SMTP/OAuth؛ metadata التخزين لا تعيد البايتات.
6. تطبيق السادسة على النسخة المستعادة فقط، والتحقق من بقاء البيانات واختبارات المدير النشط/غير النشط والمندوب والزائر. بعدها فقط إعادة خطة البصمات وتطبيق المعلق على Waseet-Test وفق التفويض المشروط. لا baseline أو reset أو repair. لا تضمين proposals تلقائياً.
7. خطة الرجوع: الاحتفاظ بالنسخة المتحققة وartifact الواجهة المتوافق مع ACL الجديدة. عند فشل السادسة تتراجع المعاملة كاملة. بعد نجاحها يفضل إصلاح أمامي؛ لا تعاد صلاحية كشف الاتصال كحل سريع. أي استعادة لاحقة تحتاج حصر الكتابات منذ النسخة وخطة حفظها وموافقة مستقلة إذا كانت ستستبدل بيانات.

## ما اختُبر محلياً بالفعل

اختبار integration_recovery يختبر حفظ صفوف التطبيق الاصطناعية، ويصنع أرشيف pg_dump فعلياً من PostgreSQL محلي ثم يستعيده في قاعدة جديدة داخل حاوية بلا شبكة أو منافذ. يقارن بيانات التطبيق وAuth fixture وسجل البصمات والمنح وRLS وتعريفات الدوال والسياسات والمشغلات والقيود، ثم يطبق السادسة ويعيد فحص الخصوصية وبقاء البيانات. المقارنة تطبع أخطاء الاختبارات فقط، ولا يستخدم الاختبار بيانات مستضافة.

هذه بروفة للأداة وبيانات اصطناعية، **وليست نسخة Waseet-Test أو إثبات استعادتها**. auth.users وStorage fixtures مبسطة؛ لم تختبر GoTrue الحقيقي أو البريد أو OAuth أو ملفات Storage الفعلية أو إضافات Supabase المدارة. لا توجد نسخة مستضافة محفوظة مستقلاً حتى الآن؛ تبقى بوابة السادسة المستضافة والإصدار مغلقة.

## فجوة اتصال أخرى منفصلة

سياسات external_listings التاريخية تتحقق من role=admin دون status=approved. المقترح `supabase/proposals/external_contacts_active_admin.sql` يضيف حدود SELECT/UPDATE/DELETE للمدير النشط، مع بقاء INSERT العام للطلبات المعلقة. اختُبر محلياً بما يشمل سياسة SELECT واسعة وحساب مدير محظور. المقترح خارج migrations ولم يطبق على أي مشروع مستضاف؛ السادسة وحدها لا تصلح هذه الفجوة. تحمي الواجهة كذلك الردود المتأخرة وتمنع رسم جهات الاتصال للحساب غير النشط، لكن حماية الواجهة لا تعوض سياسة الخادم.

## بوابة النشر الرسمي

نسخة Waseet-Test لا تحمي الإنتاج. قبل أي نشر للجميع: نسخة إنتاج مستقلة متحققة، ترقية مبنية على مخططه الفعلي دون baselines، مراجعة مقترحات الاتصال والإشعارات، CI على الرأس النهائي، واختبارات Auth/أدوار/Storage/بيع وعمولات ودردشة وبريد وPush فعلية. لا دمج ولا نشر لمجرد اجتياز البروفة المحلية أو خلو مشروع الاختبار من الصفوف.
