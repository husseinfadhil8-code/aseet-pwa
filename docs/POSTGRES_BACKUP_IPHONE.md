# تجهيز نسخة Waseet-Test من الآيفون

هذه تعليمات إعداد فقط، وليست شهادة بإنشاء نسخة. لا تستخدم Management token ككلمة مرور PostgreSQL، ولا تغيّر مشروع الإنتاج لتجهيز نسخة Test.

## خطوات الهاتف

1. في Safari افتح Supabase، ثم مشروع **Waseet-Test**، ثم **Connect** واختر **Session pooler**. انسخ إعداداته من اللوحة؛ لا تستخدم Transaction pooler ولا تختَر المشروع الرسمي.
2. في إعدادات بيئة Codex، يمكنك وضع URI كامل في السر `WASEET_TEST_DATABASE_URL`. إذا كان تحرير URI أو ترميز رموز كلمة المرور صعباً من الآيفون، استخدم بدلاً منه الحقول المنفصلة: `PGHOST` و`PGPORT` و`PGUSER` كما في اللوحة، و`PGDATABASE=postgres`، وكلمة مرور Test الحالية في سر `PGPASSWORD`. اختر طريقة واحدة؛ لا ترسل أياً من القيم في المحادثة. كلمة مرور قاعدة البيانات مختلفة عن كلمة دخول حساب Supabase.
3. أضف عبارة تشفير قوية في سر `WASEET_BACKUP_PASSPHRASE`، واحتفظ بها في تطبيق Passwords لديك. ليست مفتاح API جديداً. اسمح بمضيف Session pooler ومنفذه في TCP الخاص بالبيئة، ثم احفظ/انشر إعدادات البيئة وشغّل جلسة تطبقها. HTTP unrestricted وحده لا يمنح اتصال PostgreSQL. سيستخدم الوكيل المسار المدعوم للشبكة والتحقق الكامل من TLS؛ لن يعطّل SSL أو يتجاوز proxy.
4. بعد التصدير والتشفير واختبار الاستعادة، نزّل **الأرشيف المشفر** واحفظه عبر «مشاركة ← حفظ في الملفات» في مجلد خاص على iCloud Drive أو «على الـiPhone». لا تحتاج فتح محتوياته على الهاتف أو شراء خدمة. أعد إرفاق الملف المشفر من Files للتحقق من SHA-256 وقراءة النسخة المحفوظة خارج الجلسة. لا تُرفق عبارة التشفير أو نسخة SQL مفكوكة.

إذا لم تجد كلمة مرور قاعدة Test في مدير كلمات المرور، لا تستبدلها بـManagement token ولا تعِد تعيين كلمة مرور الإنتاج. يتوقف مسار النسخ عند هذه الخطوة إلى أن يُتاح اتصال Test مصرح به. تطوير الواجهة لا يتوقف بسبب ذلك.

## أقل إعدادات الاتصال

المطلوب مضيف ومنفذ صحيحان، قاعدة البيانات، اسم المستخدم الخاص بـTest، وكلمة مروره عبر ربط سري مناسب لعميل PostgreSQL؛ أو خدمة libpq/ملف pgpass مربوطان بأمان مع تحديد الخدمة. يلزم اتصال TCP مصرح، وعميل pg_dump من نفس الإصدار الرئيسي أو أحدث متوافق، وTLS مع `verify-full` وشهادة CA موثوقة. الوكيل يجهز أداة العميل؛ لا أوامر Terminal مطلوبة منك على الهاتف.

يُتحقق من هوية المشروع من API ومن علامة قاعدة Test قبل أي dump. لا fallback إلى رابط CLI قديم أو إنتاج. تُعامل مخرجات أخطاء الاتصال كحساسة؛ لا تُطبع URI أو كلمات المرور أو بيئة العملية أو محتويات ملفات الأسرار.

## أقل صلاحيات القراءة

للنسخة المحددة التي تغطي التطبيق وAuth وStorage metadata والتاريخ:

- `CONNECT` على قاعدة Test.
- `USAGE` على المخططات المقصودة: public وauth وstorage وsupabase_migrations وwaseet_test_ops، وأي مخططات/أنواع إضافية يكشفها الجرد كاعتماد حقيقي.
- `SELECT` على جميع الجداول والأقسام والتسلسلات المشمولة، وليس الصفوف المرئية لحساب تطبيق فقط.
- رؤية كاملة للصفوف رغم RLS. الدور المخصص للنسخ يحتاج عادةً BYPASSRLS مع منح SELECT المقيدة أعلاه؛ pg_read_all_data لا يتجاوز RLS وحده. لا تستخدم `--enable-row-security` لتخطي خطأ ثم تسمّي الناتج نسخة كاملة.
- لا حاجة لمنح INSERT/UPDATE/DELETE/CREATE أو CREATEDB/CREATEROLE/REPLICATION إلى دور النسخ. يجب مراجعة العضويات والمنح الموروثة وEXECUTE لدوال SECURITY DEFINER أيضاً؛ غياب DML المباشر ليس برهاناً عاماً ضد إساءة استعمال وظيفة أخرى.

قد لا تسمح منصة Supabase بإنشاء دور BYPASSRLS من دور المشروع العادي. لا نَعِد بأن SQL خاصاً بإنشائه سينجح ولا نطبقه تلقائياً. إذا لم يوجد دور تصدير مناسب، يمكن استعمال اتصال مدير **Test الحالي** لأول dump موثوق مع جلسة قراءة فقط وأداة موثوقة؛ هذا يقلل الإعداد الجديد، لكنه ليس اعتماداً بأقل امتيازات. لا تُنقل هذه الاستثناءات إلى الإنتاج تلقائياً.

النسخة الكاملة لكل قاعدة البيانات قد تتطلب قراءة كائنات خارج المخططات الخمسة، بما فيها بيانات إعداد الإضافات. لا تُحذف هذه الكائنات من النطاق بصمت. تُسجل الاستثناءات والملكية والمنح والأدوار دون كلمات مرور أدوار PostgreSQL، وتُراجع قابلية إعادة إنشاء إضافات Supabase قبل الاستعادة.

## حدود التغطية والاستعادة

- custom pg_dump يعطي لقطة معاملات متسقة للبيانات التي يشملها؛ جرد منفصل قبله ليس اللقطة نفسها. لا تُقارن أعداداً من وقت آخر وتصف الفرق تلقائياً كتلف.
- بيانات Auth داخل الجداول، ومنها password hashes وidentities والجلسات، حساسة ويجب أن تدخل الأرشيف المشفر إن كانت ضمن النطاق. إعدادات SMTP/OAuth ومفاتيح JWT وأسرار Edge ليست مضمونة داخل dump. استعادة الصفوف لا تثبت تسجيل الدخول أو البريد الحقيقيين.
- جداول storage تعيد metadata والسياسات، لا البايتات. يجب إعادة الجرد عند التصدير ونسخ كل الملفات المطلوبة على حدة مع بصماتها. انعدام objects المسجلة لا يثبت فحص كل ملفات الخدمة أو عدم وجود orphan objects.
- تُحفظ نسخة مشفرة مع manifest وحجم ووقت وأدوات وبصمات. تُختبر استعادتها إلى قاعدة جديدة معزولة، مع فشل صارم عند الأخطاء، والتحقق من البيانات والمخطط والملكية والمنح وRLS والقيود والتسلسلات والتاريخ. لا `--no-acl` أو تجاهل FK لإعلان نجاح كاذب.
- يلزم استرجاع النسخة من Files/iCloud والتحقق منها قبل اعتماد الاستقلال عن جلسة Codex. لا تكفي /tmp أو مساحة العمل أو نجاح بروفة اصطناعية.
- نسخة Test لا تحمي الإنتاج. أي ترقية إنتاجية تحتاج نسخته واستعادته وخطة رجوع خاصة به؛ لا تُطبق baselines على قاعدة موجودة.
