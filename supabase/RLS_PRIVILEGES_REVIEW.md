# مراجعة صلاحيات profiles وgoods

## نطاق المراجعة

المستودع هو `husseinfadhil8-code/aseet-pwa`. فُحصت نسخة `main` عند `5229ae8`، وجُلب رأس PR #6 من Git مباشرةً: `046ef14de58101e03c11bb49ffd81adf8af34fbb`. تعذرت قراءة وصف PR وتعليقاته عبر GitHub API بسبب 403؛ لا ندعي مراجعتها. الفرع `fix/supabase-rls-privilege-guards` مبني فوق PR #6، والفرق عنه ثلاثة ملفات فقط: الترحيل وهذه الوثيقة واختبارات RLS. لم يتغير `app.js` أو `atomic_sales.sql` أو التصميم في هذا الإصلاح.

لم نتصل بقاعدة Supabase الحقيقية أو نشغّل SQL عليها. السياسات المسماة `Enable update for admin` و`Allow insert goods for authenticated` غير موجودة في ملفات المستودع. أُعيد إنشاؤها في بيئة الاختبار باستخدام USING(true)/WITH CHECK(true) طبقاً للمشكلة المبلّغ عنها، وليست هذه لقطة مؤكدة لتعريفها في الإنتاج.

## النتائج والإصلاح

- اسم السياسة لا يفرض صلاحياتها: سياسة UPDATE تستخدم true تسمح بتحديث أي صف يتيحه مسار القراءة، دون التحقق من المدير. سياسة INSERT تستخدم true لا تميّز المندوب عن المدير. أثبتت الاختبارات المحلية إمكان ترقية المندوب لنفسه وإضافة غرض قبل الترحيل، ثم منعهما بعده.
- إضافة سياسة سماح جديدة خاصة بالمدير لا تلغي سياسة واسعة قديمة، لأن السياسات permissive تُجمع بـOR. يحذف الترحيل الاسمين المبلّغ عنهما على profiles/goods ويضيف حدوداً RESTRICTIVE تُجمع بـAND مع جميع سياسات السماح، حتى لو بقيت سياسات قديمة واسعة بأسماء أخرى. لا يُحذف باقي السياسات المجهولة بصورة عمياء.
- RLS تحدد الصفوف ولا تحمي أعمدة الدور بذاتها. مشغّل `guard_profile_authority` يمنع المستخدم العادي من تغيير id أو role أو status أو permissions، حتى إذا استدعى دالة SECURITY DEFINER قديمة تحاول ذلك. يسمح للمدير المعتمد بإدارة الحسابات، ويحافظ على مسارات الخادم الموثوق ذات صلاحيات BYPASSRLS.
- تحديد الخادم الموثوق يعتمد على دور جلسة PostgreSQL الفعلي، وليس current_user داخل SECURITY DEFINER ولا بيانات JWT أو user_metadata القابلة للتلاعب. لا تمنح دوراً ذا BYPASSRLS للمستخدمين. يلزم تدقيق جميع الدوال الإدارية القديمة؛ الدالة التي تستطيع تعطيل المشغّلات أو تنفيذ SQL اعتباطي بصلاحية المالك خارج نموذج حماية RLS هذا.
- تسجيل العميل متاح لمعرف auth.uid نفسه فقط، بدور rep وحالة pending وصلاحية بداية محددة `{ "can_add_inquiry": true }`. يدعم INSERT وupsert لنفس طلب التسجيل، ويرفض ترقية الحساب أو إعادة حساب معتمد إلى pending عبر إعادة التسجيل.
- عند إدراج ملف جديد من جلسة Supabase Auth الفعلية `supabase_auth_admin` دون JWT، يفرض المشغّل rep/pending وصلاحية البداية، متجاهلاً أي دور أو حالة أو صلاحيات قادمة من بيانات التسجيل. لا ينشئ هذا الترحيل مشغّل auth.users جديداً؛ يحافظ على الموجود إن وُجد. يحتاج إنشاء أول مدير إلى إجراء إداري منفصل موثوق، وليس بيانات التسجيل.
- يستطيع المندوب قراءة ملفه فقط، ويستطيع المدير المعتمد قراءة الحسابات لإدارتها. تبقى دوال الصور الشخصية واسم المستخدم وطلبات تغيير الاسم الأصلية عاملة، وفق اختبار SQL؛ لم نفتح تغيير الاسم المباشر.
- إضافة الأغراض وتعديلها وحذفها للمدير approved فقط، ويجب أن يطابق created_by المدير عند الإدراج. يستطيع المندوب approved/restricted قراءة الأغراض، بينما لا يستطيع pending/banned/removed ذلك. تُترك خصوصية أعمدة اتصال صاحب الغرض للمراجعة المنفصلة؛ الواجهة تستخدم select('*') ولا يوفر هذا الإصلاح إسقاطاً خاصاً لأعمدة المندوب.
- لا تتغير صلاحيات المبيعات أو تعريفات RPC في PR #6، ولا يُعاد منح INSERT المباشر للمبيعات. جميع اختبارات المعاملة والتزامن القديمة تعمل مجدداً تحت RLS الجديدة.
- تبقى مشغّلات إشعارات الأغراض والمبيعات والتحويل ودوال حساب المدير واشتراكات Push عاملة في الاختبارات. لم يُختبر التسليم الخارجي أو الإشعارات على أجهزة حقيقية.

## التحقق المطلوب قبل تطبيق الترحيل لاحقاً

1. راجع التعريف الفعلي للسياستين، وجميع سياسات ومنح profiles/goods، بما فيها المنح عبر PUBLIC والأدوار الموروثة. الترحيل يفعّل RLS ولا يعيد كتابة بيانات قديمة. الحسابات أو الصلاحيات المرتفعة التي عُدلت سابقاً لا تُصحح آلياً: دقّق قائمة المديرين وحالاتهم أولاً.
2. المخطط الأولي في المستودع يفتقد status وpermissions. الترحيل يتوقف عند غيابهما أو إذا لم يكن permissions من نوع jsonb، ويتطلب وجود مدير approved. تحقق من بقية أنواع الأعمدة والقيم المسموحة والتعريفات الافتراضية، واسم دور خادم Auth الحقيقي؛ لا تفترض مطابقتها لفرضية الاختبار.
3. راجع مشغّلات auth.users/profiles الفعلية. اختبار التسجيل يستخدم Auth trigger محاكياً فوق جداول PostgreSQL الحقيقية، وليس خدمة GoTrue/PostgREST المستضافة. إذا كان تأكيد البريد مفعلاً ولا توجد جلسة بعد signUp، فإن upsert في الواجهة يحتاج مسار إنشاء ملف من خادم Auth؛ لم نسمح للزائر المجهول بإدراج ملفات لحل ذلك. اختبر التسجيل المعتاد وتأكيد البريد في بيئة مرحلية.
4. طبّق الترحيل كمالك موثوق BYPASSRLS؛ دوال فحص الدور تحتاج تجاوز RLS لتجنب الاستدعاء التكراري. يفشل الترحيل إذا وجد دالة بالأسماء الجديدة يملكها دور غير موثوق، لأن CREATE OR REPLACE لا يغير المالك. راجع أيضاً أي overloads ومنح تنفيذ قديمة. لا تُجرِ bootstrap لمدير عبر تعديل بيانات مستخدم غير موثوق.
5. راجع أثر حصر قراءة الملفات بالذات/المدير على أي عميل آخر. دوال الدردشة SECURITY DEFINER تستعلم عن قائمة الفريق منفصلة، لكن المستودع يحوي مشكلات إعداد دردشة سابقة لم نصلحها هنا. أي واجهة تعتمد مباشرةً على قراءة ملفات الآخرين تحتاج مساراً محدود الأعمدة بعد مراجعة.
6. لا تُعد تشغيل ملفات تمنح وصولاً واسعاً دون مراجعة بعد اعتماد السياسة. لا تغير هذا الترحيل جداول التخزين أو external_listings أو حماية الدردشة أو سياسات المبيعات الأقدم؛ ليست هذه شهادة بأمان جميع جداول المشروع.
7. قبل التطبيق في نافذة معتمدة راجع حجم الجداول: الترحيل يقفل profiles/goods أثناء تركيب السياسات والمشغّل. اختبر على قاعدة مرحلية أولاً. لا يوجد تطبيق أو نشر تلقائي في هذا الفرع.

استعلامات وصفية مقترحة للمراجع، لم تُنفّذ على الإنتاج هنا:

```sql
SELECT tablename,policyname,permissive,roles,cmd,qual,with_check
FROM pg_policies WHERE schemaname='public' AND tablename IN ('profiles','goods');
SELECT table_name,column_name,data_type,column_default,is_nullable
FROM information_schema.columns WHERE table_schema='public'
AND table_name IN ('profiles','goods');
SELECT table_name,grantee,privilege_type FROM information_schema.role_table_grants
WHERE table_schema='public' AND table_name IN ('profiles','goods');
SELECT tgrelid::regclass,tgname,pg_get_triggerdef(oid)
FROM pg_trigger WHERE NOT tgisinternal
AND tgrelid IN ('auth.users'::regclass,'public.profiles'::regclass);
SELECT p.oid::regprocedure,r.rolname,r.rolbypassrls,p.prosecdef,p.proconfig
FROM pg_proc p JOIN pg_roles r ON r.oid=p.proowner
JOIN pg_namespace n ON n.oid=p.pronamespace WHERE n.nspname='public';
```
