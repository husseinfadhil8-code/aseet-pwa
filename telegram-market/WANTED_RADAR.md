# مطلوب في وسيط + رادار وسيط

Telegram namespace only; no changes to the original PWA, legacy schema, commissions, payments, main or experimental PR58.

- Free requests: title, structured category/governorate/area, maximum IQD budget, description and up to five private uploaded images. New/edited/renewed requests require root approval. Expiry is enforced by server time at thirty days, including public reads, offer creation, chat creation and linked radar eligibility. Closing/deleting is owner-only. Deleted data is soft retained for moderation/audit.
- Seller offers reference a seller-owned, active, approved and unreported internal listing. Existing listings can be selected; new listings use the existing editor and normal approval. Unique request/seller/listing keys and serialized quotas prevent double submits. Only request owners can read offers or start the existing membership-protected listing chat. No new public contact directory.
- Radars are private. No request is created for a standalone radar. A linked radar runs only while its request is approved and unexpired/unreported. At most ten radars/account. Exact normalized word tokens are all required; category and governorate must match, optional area must match, price cannot exceed budget. Arabic alef/yaa/diacritics are normalized; no fuzzy semantic guessing, external sources or invented inventory.
- Initial search is targeted and bounded to fifty listings. Cron scans five radars × fifty listings per minute round-robin, completing existing inventory and revisiting current revisions. This is asynchronous, not an instantaneous full-catalog guarantee. Only active approved unreported ads from nonblocked owners match; own listings excluded.
- Radar consent is explicit and separate. Global bot subscription/consent, pause/unsubscribe/block and global queue control still gate delivery. General broadcast category filters do not override a separately configured explicit radar. Disabling/editing/deleting a radar or closing its request revalidates/cancels pending deliveries. Search results remain available with notifications off. Do not promise device pushes; Telegram/device settings and prior bot interaction apply.
- A persistent unique event per radar/ad reuses the existing queue transport, leases, 429 handling, blocked-user suppression and uncertain-send review. Confirmed/uncertain deliveries are not blindly resent. Editing or reapproving the same listing cannot create another event for that radar. Recreating a deleted radar is a new subscription.
- Admin can moderate requests/reports, inspect totals of offers/radars without browsing private search text. Normal users/reps cannot call these actions. All five new tables have RLS with no direct client/service-role table grants. Narrow security-definer RPCs run behind verified Telegram initData; root operations also require configured owner and database root.

## Deployment gate

005 is additive and must not be auto-applied. The manual phase5 workflow accepts only the named development branch and exact Test project, checks digest, baseline function bodies, pinned DDL hooks, recent genuine encrypted PostgreSQL backup/isolated restore, unchanged legacy catalog, rollback fingerprint, RLS and RPC ACL. Existing001–004 must not be rerun. First rehearse/ROLLBACK, then install once with matching proof. Feature endpoints/Cron remain closed without WANTED_RADAR_ENABLED=true; enable only after matching installed proof and exact-head tests. Restore to previous Worker remains possible; retain new schema when rolling code back (no destructive down migration).

Browser fixtures and isolated PostgreSQL tests do not prove Telegram/iPhone delivery. No test subscription/ad/message is created on hosted services. Live verification must distinguish unsigned public reads, ACL failures, schema/Cron health from an owner's subsequent voluntary device journey.
