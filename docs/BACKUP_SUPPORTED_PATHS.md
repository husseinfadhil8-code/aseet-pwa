# مسارات نسخ Waseet-Test المدعومة — 25 أكتوبر 2026

لا تعِد اختبار TCP المرفوض، ولا تطلب إعادة الأسرار. لا توجد نسخة جديدة منشأة بهذه المراجعة. لا تفتح خدمة عامة لتمرير اعتماد PostgreSQL، ولا تستخدم SQL Editor أو REST لتجميع JSON وتسميته نسخة قاعدة كاملة.

## نتيجة مراجعة المصادر الرسمية

| مهمة خاصة في runner موثوق مثل GitHub Actions | الهاتف يتحكم بها عبر HTTPS، والـrunner يتصل بقاعدة Test | بديل معماري قابل للتجهيز بعد اعتماد وجهة التنفيذ وتوفر ربط سري مناسب فيها. ليس حلاً جاهزاً أو مجرباً هنا، ولا يتجاوز شبكة Codex. لا تحفظ SQL مكشوفاً في المستودع أو logs أو artifacts. |

حسب وثائق Supabase، المشاريع على PostgreSQL 15.8.1.079 والأحدث تستخدم physical backups افتراضياً. السجل السابق يرصد Test على PostgreSQL 17.11؛ هذا يرجّح المسار الفيزيائي لكنه لا يثبت الخطة أو وجود نسخة حديثة. محاولة قراءة قائمة المشاريع عبر HTTPS في هذه الجلسة رجعت HTTP 403؛ لم تُقرأ خطة Test أو قائمة نسخه الحديثة، ولم يُطلب رمز جديد. لا تستنتج من 403 أن قاعدة Test متعطلة أو أن كلمة مرورها خطأ.

## أبسط خطوة من الآيفون

افتح Safari → Supabase → **Waseet-Test** → **Database → Backups**. يكفي تحديد الحالة الظاهرة: نسخة مكتملة وخيار Restore to a New Project، أو Download لنسخة منطقية، أو غياب النسخ/طلب ترقية. لا تُرسل رابط اتصال أو كلمة مرور أو محتوى النسخة.

إذا كانت الخطة الحالية تتضمن نسخة مكتملة: النسخة التلقائية الموجودة نسخة حقيقية مستضافة. أبسط اختبار استعادة منفصل من الهاتف هو Restore to a New Project بعد مراجعة التكلفة والمهام الآلية، دون استعادة فوق المصدر. يجب اختيار نسخة حديثة مناسبة؛ النسخة اليومية قد لا تشمل آخر تغييرات اليوم. لا ننشئ مشروعاً مدفوعاً أو نغيّر الاشتراك في هذه المهمة.

النسخ الفيزيائي إلى مشروع جديد ينسخ jobs وامتدادات تتصل بالخارج مثل pg_cron وpg_net، وتبدأ بعد الاستعادة؛ لا توجد خطوة استبعاد قبل تشغيلها وفق الوثائق. لذلك يلزم فحص آثارها قبل اعتماد هذه الطريقة؛ لا تصف النسخة بأنها معزولة تماماً عن الخدمات الخارجية لمجرد اختلاف المشروع. يشمل النسخ بيانات Auth وأدوار القاعدة، لكنه لا ينسخ ملفات Storage وإعداداته أو Edge Functions أو إعدادات Auth/API كاملة. يلزم التحقق من ذلك منفصلاً.

إذا ظهر Download لنسخة منطقية: يمكن تنزيلها رسمياً من Safari، لكن حفظها خاماً في Files لا يحقق طلب الأرشيف المشفر السابق. لا نطلب رفع ملف مفكوك هنا؛ يلزم مسار تشفير موثوق والتحقق من الاستعادة قبل اعتباره النسخة المستقلة المطلوبة.

إذا كانت الخطة مجانية بلا نسخ، فلا يوجد في المصادر التي راجعناها تصدير كامل مجاني بضغطة HTTPS من Dashboard أو Management API. الحل المجاني البديل هو نقل **تنفيذ النسخ فقط** إلى runner خاص موثوق يملك TCP واعتماداً سرياً صالحاً لـPostgreSQL. يحتاج ذلك إعداد ربط اعتماد في ذلك الـrunner؛ روابط Network Secret الحالية ليست قابلة للنقل تلقائياً. لا يمكن الادعاء بإنجاز هذا المسار دون هذا الإعداد، ولا نطلب إعادة الأسرار كعلاج للبيئة الحالية. إن لم تتوفر هذه الإمكانات، فالقرار المطلوب هو توفير بيئة نسخ مناسبة أو اختيار خيار Supabase المدفوع بعد مراجعة التكلفة؛ لا توجد خطوة سرية داخل Codex تصلح النقص.

## حدود Codex في هذه المهمة

البيئة المدارة الحالية توفر مسار HTTP/HTTPS وحقن Network Secrets، ولم تثبت توفر TCP أو سر محلي صالح لعميل PostgreSQL. واجهة تعديل إعدادات البيئة المتاحة للوكيل تعرض allowed_domains وروابط أسرار HTTPS، ولا تعرض منح TCP/5432 أو تحويل هذه الروابط إلى أسرار عملية محلية. لا نعد بأن إعادة النشر أو إضافة hostname في HTTPS ستحل المشكلة.

وثائق Codex Cloud العامة تصف أيضاً أسرار setup التي تُزال قبل مرحلة الوكيل؛ هذا نموذج آخر، ولا يثبت إمكانية تحويل Network Secret الخاص بهذه البيئة إليه. لا تُكتب الأسرار في .bashrc أو مستودع أو ملف عام للتغلب على ذلك. بيئة نسخ مدعومة يجب أن توفر الإمكانيتين معاً: اتصال PostgreSQL مصرح به واعتماداً سرياً قابلاً للاستخدام في مرحلة التنفيذ.

تبقى متطلبات النسخ المستقل: لقطة متسقة تغطي المخطط والبيانات والمنح وRLS وAuth وStorage metadata وتاريخ migrations، نسخ بايتات Storage المطلوبة، تشفير قبل الرفع، manifest وبصمات، استعادة صارمة منفصلة، ثم تنزيل ciphertext إلى Files/iCloud والتحقق من النسخة المحفوظة. ملفات CSV وقراءات REST ونجاح CI ليست بديلاً. نسخة Test لا تحمي الإنتاج ولا ترفع حظر migrations عنه.
