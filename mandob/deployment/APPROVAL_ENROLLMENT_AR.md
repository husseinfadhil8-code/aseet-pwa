# التسجيل الأول بموافقة مرتبطة بمفتاح المرور — جاهز للمراجعة، غير منشور

21 نوفمبر 2026. بُني على النسخة التجريبية المنشورة 065c353. لم تُجرَ أي قراءة/كتابة Cloudflare أو ترحيل مستضاف أو نشر لهذه المرحلة. Worker الإنتاج يبقى بنظام التهيئة السابق المغلق. هذا المستند خطة التفعيل التي طلب المستخدم مراجعتها قبل إعادة النشر.

## التقييم ومقارنة الثقة
المقترح صالح إذا كانت الموافقة على مفتاح محدد وبعد إثبات صلاحية المالك، وليس على رقم طلب يرسله شخص في محادثة. Face ID يثبت تحقق الجهاز من مستخدم المفتاح؛ لا يثبت ملكية حساب Cloudflare أو استحقاق الإدارة. Passkeys قد تتزامن عبر iCloud؛ الربط هنا بالمفتاح نفسه وبكوكي المتصفح، وليس ضمان حصرية قطعة جهاز بعينها.

| البند | رمز التهيئة الحالي | الموافقة على الطلب |
|---|---|---|
| نقطة الثقة الأولى | تسليم سر عشوائي خاص للمالك | تحقق المالك عبر حساب Cloudflare المخوّل ثم الموافقة على رقم الطلب وبصمة المفتاح معاً |
| ما ينتقل للمستخدم/المشغل | رمز سري مؤقت | UUID وبصمة SHA-256 غير سريين؛ المفتاح الخاص لا يغادر المصادق |
| انتحال رقم الطلب | الرمز نفسه يمنح حق التهيئة عند حيازته | معرفة الرقم أو البصمة لا تمنح الموافقة ولا امتلاك المفتاح/كوكي الطلب |
| العمل المطلوب | قناة تسليم سر موثوقة | خطوة موافقة إدارية موثوقة وفعل إثبات سيطرة على حساب Cloudflare |
| كلفة وتعقيد | أقل طلبات وحالة مؤقتة | مزيد من طلبات D1 وبيانات معلقة؛ تضبط بنافذة قصيرة وحدود صارمة |

المسار الجديد يحل نقل السر، ولا يلغي الحاجة لإثبات المالك. لا يجوز للمشغّل أن يوافق اعتماداً على رقم منشور في ChatGPT/Codex أو صورة واجهة وحدهما.

## المنفذ في الكود
- علم ALLOW_ADMIN_APPROVAL_ENROLLMENT=false افتراضياً. لا طلبات قبل تمكينه وفتح نافذة يحددها المشغّل. فتح النافذة لا يتاح عبر HTTP.
- نافذة واحدة 10 دقائق مقترحة، وحد أقصى 15 دقيقة، وخمسة حجوزات فقط بما فيها المحاولات الملغاة. لا إعادة تعيين لعداد نافذة نشطة من أداة التحضير. بعد وجود اعتماد مدير واحد يُغلق المسار.
- يبدأ Safari WebAuthn.create مع منصة مقيمة وUV إلزامي. يتحقق Worker من origin/RP/challenge والتصديق، ثم يحفظ طلباً مع مفتاح عام فقط. لا حساب مدير ولا جلسة عند هذه الخطوة.
- رقم UUID غير سري وبصمة تربط رقم الطلب والنافذة وorigin وRP ومعرف الاعتماد والمفتاح العام وuser handle. Cookie مستقلة عشوائية 256bit، HttpOnly/Secure/SameSite=Strict تربط طلب المتصفح، ولا تظهر في الصفحة أو ChatGPT. لا public lookup/list للطلبات، ولا قبول معرف يرسله العميل بدلاً من الكوكي.
- حقول الطلب ومفتاحه غير قابلة للتعديل، بما فيها على مستوى trigger في D1. الموافقة سجل منفصل singleton؛ لا موافقات عامة أو bulk ولا endpoint عام للموافقة.
- أداة المشغّل تحضر SQL مشروطاً لمعرف الحساب وقاعدة Mandob الحاليين فقط، ولرقم وبصمة متطابقين، مع مرجع تحقق موثوق. لا تنفذ SQL أو شبكة بنفسها. تنفيذها محصور بمشغّل لديه صلاحية Cloudflare؛ مرجع التحقق ليس إثباتاً تشفيرياً بذاته ولا يؤخذ من POST عام.
- بعد الموافقة (حتى خمس دقائق وبما لا يتجاوز عمر الطلب)، يلزم WebAuthn.get بتحدٍّ جديد وتوقيع المفتاح المخزن نفسه وUV. يعيد INSERT الذرّي فحص الموافقة والبصمة والنافذة والصلاحية وغياب أي مدير. سحب الموافقة أثناء التحقق يمنع التفعيل.
- نجاح التفعيل ينسخ المفتاح الموافق عليه فقط إلى admin_credentials ويستهلك الطلب؛ لا يفتح جلسة تلقائياً. الدخول المعتاد بمفتاح المرور يصدر جلسة HttpOnly/CSRF الموجودة.
- التحديات مرة واحدة، مع ربط مستقل لنوع العملية والنافذة والطلب. يُرفض مفتاح بديل أو متصفح بلا Cookie أو نفس الاستجابة ثانية. مسار الرمز القديم يُغلق أثناء تفعيل نظام الموافقة لمنع تجاوز إجراء الموافقة.
- لا polling دوري؛ زر تحقق يدوي وزر نسخ رقم وبصمة غير سريين فقط. لا نسخ Cookie أو مفتاح خاص. حد المصادقة الموجود 10 POST لكل IP/15 دقيقة و60 إجمالاً. أصبح عداد الإجمالي يُفحص قبل إنشاء عداد IP لمنع تضخيم صفوف IP عند بلوغه. تنظيف الطلبات والقرارات المنتهية عند نشاط مصادقة تالٍ؛ ليس Cron ولا حذفاً مضموناً فور انتهاء الوقت.
- هذه حدود تطبيق، وليست ضماناً لمنع DDoS أو استنزاف الطلبات/القراءات المشتركة في الحساب. عند Free نقبل التوقف، ولا نفعّل Paid أو خدمات حماية إضافية.

## إثبات السيطرة من الآيفون دون سر
مسار مقترح قابل للتنفيذ بعد اعتماد الخطة:
1. بعد إنشاء طلبك، اضغط نسخ رقم الطلب وبصمته من Safari نفسه. النص غير سري ولا يمنح دخولاً.
2. افتح لوحة Cloudflare الرسمية في Safari وسجّل دخولك للحساب الصحيح، ثم Worker mandob-baghdad-api > Settings > Variables and Secrets. أضف متغير Text اسمه ADMIN_ENROLLMENT_OWNER_PROOF، وقيمته النص المنسوخ بالصيغة UUID:fingerprint. لا كود أو توكن أو SQL. يتطلب حفظ متغير Worker إجراء حفظ/نشر إعداد لدى Cloudflare؛ لذلك لا ينفذ الآن قبل اعتماد إعادة النشر. لا تلمس الكود أو بقية bindings/Secrets.
3. يقرأ المشغّل إعداد Worker عبر API مخوّل للحساب المعروف ويطابق القيمة مع الطلب وبصمته في D1؛ ownerMarker يرفض حساباً أو Worker أو مفتاحاً مختلفاً. لا يقبل JSON/صورة مقدمة من المتصفح على أنها نتيجة API موثوقة.
4. هذا يثبت صلاحية تغيير إعداد Worker في الحساب، وليس الهوية المدنية أو كون الشخص مالك الفوترة حصراً. يجب أن يقتصر حق هذا التغيير على المالك/المشغّل المخوّل. إذا احتاجت السياسة تمييز مالك الحساب عن المتعاونين، يُراجع المشغّل الدور/سجل الفعل عبر جلسة Cloudflare المخولة؛ إن تعذر إثبات الصلاحية المطلوبة لا تتم الموافقة. لا موافقة تلقائية من marker وحدها، ولا من رقم محادثة.
5. بعد تحقق المشغّل، يوافق على الرقم والبصمة عبر SQL المشروط في D1. ترجع إلى Safari نفسه وتضغط تحقق من الموافقة ثم تأكيد بمفتاح المرور، وتستخدم Face ID أو رمز الجهاز، ثم الدخول.
6. يغلق المشغّل نافذة التهيئة والعلم ويحذف علامة الإثبات غير السرية بعد التأكيد، ويحتفظ باعتماد المدير والجلسات الصحيحة. لا ينشر أي سر في المحادثة. فقد الكوكي أو انتهاء المهلة يتطلب طلباً جديداً منسقاً؛ قد يبقى مفتاح غير مفعل في مدير كلمات المرور ويمكن حذفه يدوياً.

البديل إن تعذر تعديل المتغير من Safari: تحقق مباشر من خلال جلسة Cloudflare مخولة أو قناة هوية موثوقة أخرى يعتمدها المشغّل. لا استبدال ذلك بصورة أو رقم عام فقط. خطوة التحقق البشري/صلاحيات الحساب ليست منفذة أو مختبرة حياً الآن.

## نتائج الاختبارات
89/89 اختباراً ناجحاً دون تخطي؛ syntax وdiff checks ناجحان. الاختبارات ببيانات ومفاتيح اصطناعية فقط، دون verify وهمية تعيد true:
- إنشاء طلب لا ينشئ مديراً أو جلسة، وغياب الموافقة يمنع التفعيل.
- منع تبديل المفتاح، والبصمة المخالفة والتوقيع بمفتاح آخر والكوكي المفقودة وادعاء role=admin.
- انتهاء الموافقة/النافذة، وإلغاء الموافقة بعد إصدار التحدي، وحتى إلغاؤها بعد التحقق من التوقيع وقبل INSERT.
- خمسة حجوزات كحد أقصى، وعدم إعادة تعيين النافذة الحية، وغلق العلم الافتراضي والرمز القديم، وحجب origin أجنبي.
- أدوات المشغّل ترفض مشاريع/حسابات أخرى وعلامة مالك غير مطابقة؛ الأدلة نفسها اصطناعية وليست تحقق هوية مستخدم حقيقي.
- bundle Worker الفعلي مع D1 محلية أصلية: طلب وتحقق تسجيل، موافقة مشغّل اصطناعية، توقيع تفعيل جديد، ثم تسجيل دخول وإتاحة API للإدارة.
- Chromium بمصادق افتراضي 390×844: طلب، عرض UUID وبصمة، موافقة عبر إشارة محلية للمشغّل (لا endpoint موافقة)، تحقق وتفعيل ودخول وإلغاء الجلسات؛ بلا أخطاء JS أو overflow. ليس Safari أو Face ID حقيقيين ولا اختبار TLS إنتاج.

## خطة إعادة النشر — تحتاج الموافقة أولاً
1. التحقق من Free والحصص المشتركة وهوية Worker وD1 الحاليين. لا موارد جديدة.
2. نسخة منطقية لقاعدة Mandob فقط (التصدير القياسي لا يدعم FTS5 كما ظهر سابقاً) واختبار استعادتها، مع إبقاء DATA_KEY منفصلاً. تطبيق migration 0006 فقط بعد التحقق من النسخة؛ الإضافات جداول وتوسعة تحديات، دون حذف بيانات.
3. نشر الكود أولاً والعلم false، مع بقاء Messenger/AI/media/sends/alerts false وFREE_ONLY=true. لا Access أو Queue أو R2 أو Gateway.
4. اختبارات سحابية اصطناعية وقياس CPU/D1؛ CPU p99 السابق قريب من 10ms ولذلك لا نضمن سلوك Free من اختبار محلي، ولا نرفع الخطة إذا احتاج تحسيناً. إزالة اعتمادات الاختبار فقط.
5. بعد نجاحها، فتح نافذة منسقة وتمكين طلبات الموافقة لتهيئة المدير الحقيقي. إجراء إثبات السيطرة والموافقة المحددة والتوقيع الجديد، ثم إغلاق استقبال الطلبات وإزالة marker. تأكيد Safari/Face ID على جهازك مطلوب.

لا توجد تغييرات على Production في هذه المهمة؛ migration 0006 لم تطبق سحابياً، والعلم الجديد لم يُفعّل. لا ادعاء أن زر طلب التسجيل يعمل حالياً في الموقع المنشور. Messenger والذكاء الاصطناعي خارج نطاق التفعيل.
