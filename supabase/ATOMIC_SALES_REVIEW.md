# مراجعة تسجيل البيع الذرّي

هذا تغيير للمراجعة فقط. لم تُشغّل `atomic_sales.sql` على Supabase الحقيقي، ولا ينفّذ التطبيق ترحيلاً تلقائياً.

## السلوك

- يستدعي `app.js` دالة `record_sale` مرة واحدة بدلاً من إدراج البيع ثم تحديث الغرض بطلبين.
- تستخدم الدالة `auth.uid()`؛ تشترط مديراً بحالة `approved` ومندوباً بدور `rep` وحالة `approved` أو `restricted`، وفق نموذج التطبيق الحالي.
- تثبّت صفّي المدير والمندوب بقفل `FOR SHARE` حتى لا تتغير صلاحياتهما أثناء المعاملة، ثم تقفل الغرض بـ`FOR UPDATE` وتتحقق أنه `available`.
- تتحقق قاعدة البيانات من مبالغ صحيحة بالدينار: سعر أكبر من صفر، إجمالي عمولة غير سالب، وحصة مندوب بين صفر والإجمالي. الحد الأعلى `9007199254740991` للحفاظ على دقة JavaScript. ترفض الكسور وNULL وNaN وInfinity.
- تحسب قاعدة البيانات حصة الإدارة، وتحدد الموثّق ووقت التوثيق. لا تفرض 50/50 أو مساواة العمولة بالعمولة المتفق عليها؛ الواجهة الحالية تسمح بتحديد الحصص يدوياً.
- إدراج البيع وتسجيل أهلية الغرض وتحديث حالته وإشعارات SQL الحالية ضمن المعاملة نفسها. فشل أي منها يعيد الجميع إلى حالتهم السابقة. Push الخارجي يبقى بعد نجاح RPC، كما في التطبيق؛ ليس جزءاً من معاملة PostgreSQL.
- يمنع `sale_goods_registry` تسجيل بيع جديد لنفس `goods_id` بمفتاح أساسي. تُدرج معرفات المبيعات القديمة مرة واحدة مع إبقاء جميع صفوف المبيعات، حتى المكررة، دون تعديل. المشغّل يمنع الإدراج المكرر حتى عبر مسار ذي صلاحيات مرتفعة، ويمنع تغيير `goods_id` لبيع موجود.
- يبقى سجل الأهلية بعد حذف سجل البيع: حذف البيع أو إعادة حالة الغرض إلى `available` لا يسمح ببيعه مجدداً. حذف السجل المالي الحالي وتأكيد التحويل ما زالا متاحين بصلاحياتهما القائمة. إعادة البيع الفعلي/الإرجاع تحتاج نموذج إلغاء مستقل، وليست جزءاً من هذا الإصلاح.
- تُسحب صلاحيات INSERT المباشرة من PUBLIC وanon وauthenticated، بما فيها منح الأعمدة؛ سياسات القراءة والحذف ودالة تحويل العمولة لا تتغير. الدالة تستخدم `SECURITY DEFINER` و`search_path` فارغاً وأسماء جداول مؤهلة بالكامل، وتتاح فقط لـauthenticated بعد فحص المدير داخلها.
- الواجهة تمنع النقر المكرر أثناء الطلب، وتحافظ على النموذج عند الخطأ، ولا ترجع إلى الكتابتين المنفصلتين إذا لم تُثبّت الدالة.

## ما يحتاج التحقق في قاعدة البيانات الفعلية قبل أي تطبيق

المستودع لا يحتوي لقطة معتمدة للمخطط الفعلي. لم نتصل بقاعدة الإنتاج في هذه المهمة.

1. `supabase-schema.sql` مخطط أولي يفتقد `profiles.status`، بينما التطبيق و`fix_sales_permissions.sql` يعتمدان عليه. الاختبارات تضيف هذا العمود صراحةً كفرضية، لا كإثبات عن الإنتاج. الترحيل يتوقف إذا غاب عمود مطلوب أو اختلف نوع UUID/bigint/timestamptz المتوقع، أو لم تكن RLS مفعّلة للمبيعات.
2. تحقق من أنواع role/status وقيمها، ولا سيما أن المدير الشرعي `approved` وأن حالة الغرض تقبل `sold`. الحسابات الإدارية ذات الحالة NULL أو غير المعتمدة ستُرفض بأمان. لا تغيّر البيانات آلياً لمعالجة الاختلاف.
3. راجع جميع سياسات RLS ومنح الأعمدة والأدوار الموروثة، خصوصاً منع المندوب من تعديل `role`/`status`/`permissions` في `profiles`. هذا الإصلاح لا ينشئ سياسات الجداول الأساسية المفقودة من المستودع ولا يثبت صحة الموجودة بالإنتاج.
4. راجع كل مشغّلات `sales` و`goods` ودوال SECURITY DEFINER والكتّاب الآخرين للمبيعات. على العملاء استخدام RPC؛ الحسابات الخدمية الموثوقة لا ينبغي أن تستمر في مسار الإدراج والتحديث المنفصلين. المشغّل يحمي التفرد، لكنه لا يحوّل أي مسار إداري خارجي إلى RPC تلقائياً.
5. راجع `notifications` و`category='sale'` ومشغّلات إشعارات البيع الحالية، لأنها قد تمنع البيع كله إن كان مخططها غير متوافق. اختُبرت الملفات الموجودة محلياً، لكن لا يوجد إثبات أنها نفسها المثبتة بالإنتاج.
6. احصر المبيعات المكررة والأغراض ذات سجل بيع وحالة `available`، والأغراض المباعة دون سجل. لا يحذف الترحيل أي حالة قديمة ولا يصححها. السجل الداخلي يمنع إضافة بيع جديد لكل غرض له تاريخ بيع حتى لو كانت حالته القديمة خاطئة.
7. راجع حجم الجدول ونافذة صيانة مناسبة: الترحيل يقفل جدول المبيعات أثناء إدراج المعرفات التاريخية وتركيب المشغّل. يجب أن يملكه مالك موثوق يستطيع تنفيذ الدالة وكتابة الجداول مع RLS، دون توسيع وصول العملاء.
8. تأكد من عدم وجود جدول أو دوال مخصصة مسبقاً بالأسماء الجديدة. افحص المالكين والامتيازات وتوقيعات `record_sale` وأي overloads قبل اعتماد الترحيل.

يمكن للمراجع جمع البيانات الوصفية التالية بقراءة فقط، بعد الحصول على صلاحية مراجعة قاعدة الإنتاج. هذه استعلامات مقترحة ولم تُنفّذ هنا:

```sql
SELECT table_name, column_name, data_type, udt_name
FROM information_schema.columns
WHERE table_schema='public' AND table_name IN ('profiles','goods','sales','notifications')
ORDER BY table_name, ordinal_position;

SELECT tablename, policyname, roles, cmd, qual, with_check
FROM pg_policies WHERE schemaname='public'
AND tablename IN ('profiles','goods','sales','notifications');

SELECT grantee, privilege_type FROM information_schema.role_table_grants
WHERE table_schema='public' AND table_name='sales';

SELECT grantee, column_name, privilege_type FROM information_schema.column_privileges
WHERE table_schema='public' AND table_name='sales';

SELECT tgrelid::regclass, tgname, pg_get_triggerdef(oid)
FROM pg_trigger WHERE NOT tgisinternal
AND tgrelid IN ('public.sales'::regclass,'public.goods'::regclass);

SELECT count(*) AS goods_with_duplicate_sales FROM (
  SELECT goods_id FROM public.sales GROUP BY goods_id HAVING count(*)>1
) duplicates;
```

## ترتيب المراجعة والتطبيق لاحقاً

بعد الموافقة والتحقق من مخطط بيئة اختبار Supabase أولاً: تُطبق متطلبات المخطط وسياسات القراءة/الحذف وإشعارات SQL الموجودة، ثم `atomic_sales.sql` أخيراً كمالك موثوق. لا تُعد تشغيل `fix_sales_permissions.sql` بعده دون مراجعة لأنه يعيد منح INSERT المباشر. افحص أن `authenticated` لا يملك INSERT على الجدول أو أعمدته، وأن EXECUTE متاح للدالة للمستخدمين المسجلين فقط، وأن حالات الصلاحيات والتزامن تمر على بيئة الاختبار. ثم يمكن نشر الواجهة في إجراء منفصل معتمد. لا تنشر الواجهة قبل تثبيت الدالة؛ عند غيابها يفشل الحفظ بأمان دون كتابة جزئية. لا توجد عودة تلقائية أو حذف للسجل الداخلي ضمن هذا التغيير.

## الاختبارات المحلية

```bash
# تنزيل صورة PostgreSQL الرسمية؛ لا توجد مفاتيح أو اتصال بقاعدة حقيقية.
docker pull postgres:17
PYTHONDONTWRITEBYTECODE=1 python3 scripts/integration_atomic_sales.py -v
# يتطلب Playwright ومتصفح Chromium مثل اختبار الأمان الموجود.
PYTHONDONTWRITEBYTECODE=1 python3 scripts/browser_app_security.py -v
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts -p 'test_*.py' -v
node --check app.js
git diff --check
```

اختبارات SQL تنشئ حاوية مؤقتة جديدة دون شبكة أو منافذ أو ملفات مركبة، وتزيلها عند النهاية. لا تقبل DSN أو مفاتيح Supabase. تشمل النجاح والرفض والصلاحيات والمدخلات والتراجع عند فشل المشغّلات والإشعارات، والتزامن الحقيقي بين اتصالين، والحفاظ على التاريخ وتكرار الترحيل وتحويل العمولة والحذف. اختبارات المتصفح تحجب الاتصالات الخارجية وتختبر RPC الوهمي؛ لا تثبت تسليم Push أو إعدادات PostgREST/JWT/RLS على المشروع الحقيقي.
